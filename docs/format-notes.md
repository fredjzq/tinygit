# 实现笔记：Git 的磁盘格式

这份文档记录实现过程中真正卡住过的地方。不是 Git 教程的复述，而是「按文档写代码时会踩什么坑」。

## 一、对象：为什么哈希要包含头部

直觉上会觉得「文件名 = 内容的哈希」。实际是：

```
sha1("<type> <size>\0" + content)
```

三个后果：

1. **类型参与哈希**。空 blob 和空 tree 内容都是空，但哈希不同：
   - `blob 0\0` → `e69de29b...`
   - `tree 0\0` → `4b825dc6...`
2. **长度参与哈希**。解析时能先知道内容应该多长，读截断的文件会立刻报错，而不是解析出垃圾数据。
3. **完整性自证**。文件名就是校验和，读到损坏的数据重算一遍就能发现。

### size 是字节数，不是字符数

中文 `"中文"` 是 2 个字符、6 个字节。头部必须写 6。这个 bug 在测试里专门加了一条：

```js
const decoded = decodeObject(encodeObject("blob", "中文").raw);
assert.equal(decoded.content.length, 6);  // 不是 2
```

## 二、tree 排序：最反直觉的一条规则

Git 的 tree 条目按名字排序，但**目录要当作名字后面加了 `/`**。

因为 `'/'` (0x2f) 小于 `'t'` (0x74)，所以：

```
foo.txt   ← 排在前面
foo/      ← 目录，排在后面
```

如果按普通字典序，`foo` 会排在 `foo.txt` 前面，**tree 哈希就和真 Git 不一致**。后果不是「看起来不对」，而是真 Git 认为仓库被篡改。

实现里用一个 `sortKey` 函数处理：

```js
function sortKey(entry) {
  return entry.type === "tree" ? entry.name + "/" : entry.name;
}
```

并且比较用 `Buffer.compare`（字节序）而不是 `localeCompare`（语言环境相关，不可靠）。

## 三、索引：唯一需要精确控字节的地方

`.git/index` 是二进制文件。布局：

```
┌─────────────────────────────────┐
│ "DIRC"            4 字节         │
│ version           4 字节 (BE)    │
│ entry count       4 字节 (BE)    │
├─────────────────────────────────┤
│ 条目 1: 62 字节固定头 + 路径 + 填充│
│ 条目 2: ...                      │
├─────────────────────────────────┤
│ SHA-1 of everything above        │  ← 20 字节
└─────────────────────────────────┘
```

### 填充规则

每条目总长度对齐到 8 字节：

```js
const entryLength = (62 + nameLength + 8) & ~7;
```

+8 是为了包含至少 1 字节 NUL 终止符再加上余量，`& ~7` 向下取整到 8 的倍数。

### 固定头里的字段顺序

ctime / ctimeNano / mtime / mtimeNano / dev / ino / mode / uid / gid / size / sha / flags。

注意 **sha 在 mode 之后、uid/gid 之前是不对的** —— 实际是：mode(24) uid(28) gid(32) size(36) sha(40..60) flags(60)。写错顺序会导致所有字段偏移错位。

### 校验和覆盖范围

末尾 20 字节是**前面全部内容**的 SHA-1，不包括自己。测试里显式验证：

```js
const body = buf.subarray(0, buf.length - 20);
const checksum = buf.subarray(buf.length - 20);
assert.equal(createHash("sha1").update(body).digest("hex"), checksum.toString("hex"));
```

## 四、diff：Myers 算法为什么快

朴素做法是 LCS 动态规划，O(N×M)。两个 1000 行的文件要 100 万次比较。

Myers 的思路不同：把问题看成「编辑距离为 d 时能走到哪」。

- d 从 0 开始递增
- 每个 d 只考虑能到达的对角线 k ∈ [-d, d]
- 沿每条对角线尽量向右下延伸（相同的行直接跳过）
- 一旦到达终点 (N, M)，d 就是最短编辑距离

复杂度 O((N+M)·D)。**D 是实际差异数**，代码改动通常很小，所以远快于 LCS。

实测：连续插入/删除场景下，D 远小于 N，表现接近线性。

### 回溯

正向只记录「每步走多远」，要拿到具体操作得**反向回溯**。实现里把每轮 v 数组存下来（`trace`），回溯时对比前后两轮判断这步是删除还是插入。

陷阱：回溯时`k === -d` 与 `k !== d && v[k-1] < v[k+1]` 的判断要和正向完全对称，否则会少走或多走一步，产生「删了又加同一行」的冗余 diff。

## 五、可执行位：平台差异

Git 用 mode `100644`（普通）/ `100755`（可执行）区分。

**Windows 上没有 POSIX 执行位**。NTFS 下：

```js
await chmod(file, 0o755);
(await stat(file)).mode.toString(8);  // 仍然 "100666"
```

所以「chmod 后提交，检出后仍是可执行」这条在 Windows 上无法验证。测试里用 `skip` 处理，而不是伪造一个假的通过。

另一个坑：索引里存的 mode 是**十进制**（`33188` = `0o100644`），但它同时可能是完整 `st_mode`（含 `S_IFREG` 位）。所以规范化时不能一律 `parseInt(x, 8)`：

```js
// 字符串 "100644"  → parseInt(_, 8)
// 数字 33188        → 取低 12 位权限位再判断
```

这个区别一开始就写错了，导致可执行位丢失。

## 六、为什么另写一个验证器

如果验证器调用被测代码，那个函数有 bug 时两边一起错，测试照样「通过」。

所以 `scripts/verify.mjs` 完全独立：自己实现 inflate、自己算哈希、自己解析索引。它只依赖 Git 格式的字节布局描述。

这样才有意义：**两份独立实现得出相同结论，才说明格式是对的。**
