# 实现笔记（二）：packfile 与三方合并

这是难度提升后新增的核心部分。两块都是 Git 里公认难写的部分，也都踩到了真 bug。

## 一、packfile 为什么难

松散对象的解析只是「读文件、解压」，而 packfile 有四个叠加的复杂度：

1. **没有长度前缀**：zlib 流自己不知道在哪结束
2. **delta 压缩**：大多数对象不存内容，只存「相对另一个对象的差异」
3. **delta 链**：delta 的 base 本身可能也是 delta，最多 50 层
4. **变长整数**：两种不同规则，混用就错

### 1. 对象边界：zlib 不告诉你它读了多少

这是最反直觉的坑。

```js
// 你以为会知道消耗了多少字节：
const out = inflateSync(buf.subarray(start));
// 实际：Node 的 inflateSync 会静默忽略尾部多余字节，
// 而且不返回「消耗了多少输入」。
```

pack 里对象紧密排列，必须知道每个 zlib 流的确切长度才能找到下一个对象。

**解法**：zlib 流末尾有 adler32 校验和，**截断的输入必然解压失败**。
所以「能成功解压的最短前缀」恰好等于流长度。对它二分：

```js
// 先用理论压缩率估算上界，避免从 2 字节开始扫
const guess = Math.max(64, Math.ceil(expectedSize * 1.05) + 64);
// 然后在 [2, guess] 上二分，找最小的可行长度
```

这个方案可靠但有代价：每个对象约 20 次 inflate 尝试。
3,513 个对象用了约 1.1 秒。真 Git 用 C 直接读 inflate 的 total_in 字段，几乎零开销——
这是语言层面的差距，不是算法错误。

### 2. 两种变长整数，规则不同

**OFS_DELTA 的偏移**编码有个 +1 修正：

```
offset = byte0 & 0x7f;
while (byte0 & 0x80) {
  byte0 = next;
  offset = ((offset + 1) << 7) | (byte0 & 0x7f);   // ← 注意这个 +1
}
```

**delta 头部的大小**编码没有这个修正，就是普通位拼接。

为什么 OFS 要 +1：让续字节与终止字节的编码空间不重叠，保证同一偏移只有唯一编码。
漏掉它，偏移会偏小，读到错误的 base。

### 3. delta 指令流

每条指令首字节高位决定类型：

| 首字节 | 含义 |
| --- | --- |
| `1xxxxxxx` | 复制：从 base 的某处拷一段 |
| `0xxxxxxx` | 插入：后面 N 字节是字面数据 |
| `00000000` | 非法（长度为 0 的指令无意义）|

复制指令的偏移和长度都是**按需字段**——首字节的各个位分别指示对应字节是否存在。
这是紧凑编码，但极容易写错。还有一个陷阱：

```js
// 长度字段全为 0 时表示 0x10000（65536），不是 0
if (size === 0) size = 0x10000;
```

忘了这条，大段复制的长度会被当成 0，结果整个对象内容丢失。

### 4. idx 文件的两个坑

**坑一：尾部 40 字节的顺序**。第一次写反了：

```
[len-40, len-20)  →  pack 文件内容的 sha1
[len-20, len)     →  idx 文件自身（前 len-20 字节）的 sha1
```

怎么发现的：pack 文件名就是 pack 校验和。解析真实仓库时算出来的值与文件名不符，立刻暴露。

**坑二：idx 自校验和覆盖到哪**。直觉是覆盖「前面所有内容」，实际**不包含 pack 校验和**：

```js
idxChecksum = sha1(body)              // body 到 packChecksum 之前结束
// 不是 sha1(body + packChecksum)
```

这个区别看不出对错，只能实测真文件比对。

### 验证结果

用本机一个真实 Git 仓库的 pack（7.8 MB，3,513 个对象）验证：

```
声明对象数   : 3513
解析出对象   : 3513
偏移→sha 一致: 3513/3513  ✅
类型分布     : {commit:1, tree:1294, blob:2218}
```

第二条是决定性证据：只要 delta 链、对象头、zlib 边界任意一处出错，
重新计算的 sha 都不可能和 idx 里的记录吻合。

## 二、三方合并

### merge base 的判据（这里真错过一次）

要合并两个分支，先找它们的最近公共祖先。

公共祖先可能有很多个。判据是：**candidate 是最近公共祖先 ⟺ 不存在其他公共祖先 X，使得 candidate 是 X 的祖先**。

直觉：如果 candidate 还是某个更远节点的祖先，说明它本身也不够近。

**第一次写成了反向**：

```js
// 错误写法：
const hasCloserCommon = common.some(
  (other) => candidateAncestors.has(other.oid)   // X 是 candidate 的祖先
);
if (!hasCloserCommon) return candidate.oid;
```

为什么错：最近的节点当然拥有更多更远的祖先。这个条件对正确答案永远成立，
于是正确答案被跳过，一路退到最远的根提交。

**后果不是崩溃，而是产生假冲突**：

```
分支点:        c2  ← 正确答案
             /  \
        main      feature
     (改 README)  (改 math.js)

两边改的是不同文件，本该无冲突。但 merge base 错成 c1 后，
diff 出来两边都在「新增 mul 函数」，于是判定同一区域双方都改了 → 假冲突。
```

这个 bug 很隐蔽：只有在「分支点不是根提交、且两边改动的文件相对分支点有重叠内容」时才暴露。
简化测试（分支点就是根提交）不会触发。

### 零宽区间：纯插入的重叠判定

三路归并把每个变更块表示成 base 坐标上的区间 `[baseStart, baseEnd)`。

但**纯插入**产生的区间是零宽的：`baseStart === baseEnd`。

于是两个在同一位置插入不同内容的块，用 `next.baseStart < groupEnd` 判断重叠会失败
（此时 `groupEnd === baseStart`，`1 < 1` 为假），两个插入被当成独立处理，
结果两边的行同时出现——既不冲突，也不正确。

**修正**：零宽块与端点相接时也要归入同一组。

```js
const overlaps = next.baseStart < groupEnd
  || (next.baseStart === groupEnd && (next.baseEnd === next.baseStart || ...));
```

同时要小心**不能过度合并**：分别在不同位置（如 head 和 tail）插入的两个块必须独立应用。
测试里两种情形都有覆盖。

### 分段模型统一两套输出

归并需要两种结果：

1. 自动合并的完整内容（成功时）
2. 带冲突标记的文件（冲突时）

如果分别实现两套逻辑，迟早不一致。所以引入 `mergeSegments` 产出统一的分段序列：

```js
{ kind: "same", lines }                 // 两边一致
{ kind: "ours", lines }                 // 仅 ours 改
{ kind: "theirs", lines }               // 仅 theirs 改
{ kind: "conflict", ours, theirs }      // 两边都改且不同
```

`merge3` 和 `renderMergedFile` 都从它派生，保证行为一致。

## 三、测试策略

| 层次 | 手段 | 能发现什么 |
| --- | --- | --- |
| 编码单元 | varint / delta 往返 | 位运算错误、边界值 |
| 闭环 | 自己写 pack 再自己读 | 写入端与读取端不一致 |
| 真实数据 | 读真 Git 生成的 pack | 与规范的真实偏差（关键）|
| 端到端 | 造分支、真合并 | 集成逻辑错误 |

其中「真实数据」这层不可替代。自己造的数据只能验证「我的理解自洽」，
真 Git 的 pack 才能验证「我的理解正确」。idx 校验和那两处错误都是这一层发现的。

## 四、还没做的

- **写 delta**：目前只写完整对象，能读 delta。写 delta 需要找相似对象、
  算最小编辑脚本、控制链深度，工作量接近再写一遍这一层
- **thin pack**：REF_DELTA 的 base 在 pack 之外的情形，需要外部对象查找
- **增量重建 / 多 pack 索引**：真仓库可能有多个 pack 和 midx
- **rename 检测**：合并时不会识别「文件改名」，会当成删除+新增
